# WaveDevSecOps v0.2.0 : les stations 1 à 3 de la chaîne

Deuxième version testable. Elle ajoute au socle git de la v0.1.0 les trois premières stations de la
chaîne DevSecOps, dans les deux parcours, toujours hors ligne. Elle n'envoie aucune télémétrie et ne
fait aucun appel réseau, sauf l'exécution facultative du code LLM.

## Contenu de la v0.2

- **Chaîne de livraison** : bandeau des quatre stations et carte dépliable (barrières, outils, liens
  vers checks, hooks et termes), page Vocabulaire reliant chaque terme à sa barrière, encart « Ce qui
  l'aurait bloqué » dans les scénarios B. Les stations 1 à 3 sont livrées ; la station 4 (livraison)
  arrive en v0.3.
- **Outils hors ligne** : ruff, pytest, gitleaks, bandit, pip-audit, coverage et diff-cover tournent
  depuis un cache préchargé, réseau coupé ; ruff et pytest se lancent dans le terminal du bac à sable.
- **Pipeline simulé sur chaque PR**, en 7 jobs : ruff, pytest, gitleaks, bandit, pip-audit, `uv lock
  --check` et quality gate de couverture (80 % du nouveau code). Même pipeline lu en GitHub Actions,
  Jenkins et GitLab CI ; revue obligatoire et protection de la branche `main` simulées.
- **Scénarios de station** (parcours sans IA et parcours LLM) : `defaut-de-lint`, `test-casse`,
  `secret-dans-un-commit` (hook pre-commit gitleaks), `check-en-echec`, `pr-sans-revue`,
  `push-direct-main`, `code-vulnerable` (bandit), `dependance-vulnerable` (pip-audit et SBOM, base de
  vulnérabilités locale et figée), `couverture-sous-le-seuil` (quality gate), puis les scénarios LLM
  `outil-trop-puissant`, `cle-api-en-dur` (gitleaks, test de config contre l'envoi au cloud) et
  `donnees-vers-le-cloud`, avec l'injection de prompt nommée en revue.
- **Explications de la vue pipeline** (check, tâche, sortie) et terme « traçabilité » qui mène à la
  vue Distant + PR.
- **Arbitrages d'interface** : confirmation de `rm -rf *`, Échap du mode Désigner, notice effacée à
  l'enregistrement, « i » des références hors du bouton du commit.

## Installer cette version

Les commandes du README installent la tête de `main`. Pour installer exactement la v0.2.0, posez
`WDS_INSTALL_REF=v0.2.0` et téléchargez l'installeur de la même étiquette :

```sh
curl -fsSL https://raw.githubusercontent.com/Aliquanto3/wavedevsecops/v0.2.0/install.sh | WDS_INSTALL_REF=v0.2.0 sh
```

```powershell
$env:WDS_INSTALL_REF = 'v0.2.0'
```

puis la commande Windows du README, en remplaçant `/main/install.ps1` par `/v0.2.0/install.ps1`.

## Limites connues

Ce sont des limites de principe, nommées aux débriefs des scénarios, pas des défauts à corriger.

- **Couverture** : un test sans assertion qui exécute le code fait passer le seuil de 80 %. Le code
  de l'apprenant tourne dans le processus qui mesure : un `conftest.py` peut réécrire la mesure. La
  quality gate ne remplace pas la revue humaine. Le seuil porte sur un total, pas sur chaque fichier.
- **Tests** : un test écarté par la configuration de pytest (et non par le code du test) échappe
  aux contrôles du scénario LLM.
- **Secrets** : une clé découpée ou encodée échappe à gitleaks.
- **Bandit** : `getattr(builtins, "ev" + "al")` et formes voisines passent sans constat ; le
  scénario `outil-trop-puissant` les ferme en lisant le fichier de l'outil, pas bandit.
- **Liste de noms interdits** : les contrôles du scénario LLM reposent sur des listes de noms
  d'outils et de fonctions ; un nom absent de la liste n'est pas détecté.
- **Contrôles navigateur restants** : le rendu des pages Vocabulaire, carte de la chaîne et
  explications du pipeline n'a pas été vérifié par un humain sur plusieurs navigateurs.
- **Vérifications sur poste réel** toujours en attente (voir les notes de la v0.1.0) : Windows non
  administrateur derrière un proxy, macOS et Linux sur poste personnel, exécution LLM avec Ollama.
- **Station 4 (livraison)** : absente, annoncée « Arrive en v0.3 ».
