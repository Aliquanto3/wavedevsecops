git-commands-training

Appli locale pour apprendre git et GitHub, puis la chaîne CI/CD et DevSecOps, sur le modèle pédagogique de WaveStack. Public : Anaël, puis des collègues en vibe coding (en autonomie, puis en atelier), puis des clients.

Issue : idée durcie. C'est un seul produit, présenté à la v1.0.0, avec des releases 0.x à chaque lot.

Après la v0.1 : un test avec deux collègues pendant une heure s'ils sont disponibles, sinon les propres tests d'Anaël.

Décisions verrouillées · socle git

  • Mécanique : l'apprenant tape les commandes (A). Dans les scénarios B, un agent a agi sur le dépôt, et l'apprenant comprend ce qui s'est passé puis décide.
  • Moteur : vrai git sur un dépôt bac à sable, un dépôt bare local qui joue origin, et une couche « GitHub simulé » pour les PR, la revue, le merge et les commits d'un collègue. Tout fonctionne hors ligne.
  • Agent B : scénarisé et déterministe, avec des erreurs réalistes prévues.
  • Deux parcours : l'un avec du code LLM en décor (exécution facultative, pas de leçon sur le fonctionnement des agents), l'autre avec du code minimal sans IA.
  • Points d'ancrage pour la suite : scénarios en YAML déclaratif, modèle de PR avec des checks, dépôts d'exercice avec tests/, mise en page qui accepte un volet supplémentaire.

Décisions verrouillées · chaîne DevSecOps

  • Concepts et barrières, montrés avec de vrais outils légers : ruff, pytest, pre-commit, gitleaks, bandit, pip-audit. Jenkins, GitHub Actions et GitLab CI sont montrés comme trois écritures du même pipeline. Sonar est présenté comme une quality gate simulée.
  • La station 3 (sécurité et qualité) est le cœur, parce que c'est ce que regardent RSSI, DSSI et conformité. Elle inclut des barrières propres au code LLM : clé en dur, outil trop puissant, données envoyées au cloud. L'injection de prompt est seulement nommée.
  • Savoir en parler : un scénario « entretien RSSI » où chaque réponse s'appuie sur une preuve dans les vues, une fiche exportable barrière → risque → preuve, et la conformité en simple correspondance.
  • CI et CD : une vue « carte de la chaîne » suit l'apprenant et fait apparaître la frontière entre les deux.
  • Réussite v1.0 : installation complète en moins de 10 min, sans droits administrateur et hors ligne ; séances d'une heure au plus ; entretien RSSI réussi à 80 % ou plus du premier coup ; tous les scénarios terminés sans indice.

Rejeté, et pourquoi

  • Git simulé en JavaScript : le terrain est déjà occupé et les messages affichés ne sont pas fidèles.
  • Chatbot tuteur avant la v1.0 : il risque de casser en démonstration, et le routage vers plusieurs endpoints coûte cher.
  • Un vrai LLM qui pilote git : son comportement n'est pas déterministe, ce qui désynchroniserait les quiz.
  • Vrais Jenkins et SonarQube : ce sont des serveurs Java lourds, qui casseraient l'installation légère.
  • L'agentique comme objectif pédagogique : elle ajouterait une deuxième charge cognitive.
  • Deux produits V1 et V2 successifs : remplacés par un seul produit à jalons.

Points faibles qui restent ouverts

  • Installer git, gitleaks et les autres outils sans droits administrateur.
  • pip-audit interroge une base en ligne. Il faudra embarquer un instantané de la base ou simuler le résultat.
  • La sauvegarde et la restauration du bac à sable doivent être fiables, pour les quiz où la mauvaise commande est exécutée.
  • Le développement se fait d'un seul bloc jusqu'à la v1.0. Le retour des collègues après le socle git n'est pas garanti, et la vue du graphe des commits, qui porte tout le reste, risque de n'être validée que par son auteur.
  • Le nom, la licence et la stack ne sont pas tranchés.

Plus tard

  • Mode formateur pour les ateliers, mode connecté à un vrai GitHub.
  • Chatbot qui appelle Ollama et des endpoints cloud, vocabulaire GitLab (MR), commandes cherry-pick et bisect.
  • Version anglaise, hébergement sans installation, suivi de plusieurs apprenants.
  • Docker, Kubernetes et l'infrastructure as code, au mieux dans un glossaire.
